git rebase as a thinking tool

2026-03-30 · [deep dive]

i used to be afraid of `rebase -i`. now i use it like a journal. how editing your history makes you a clearer thinker, not just a tidier committer.

for a long time i thought rebase was for people with stronger opinions about commit history than i had. turns out the opinions came after.

the unlock

the mental shift was treating my branch as a draft, not a record. the first pass of commits is stream-of-consciousness:

wip
wip 2
ok this works
forgot the test
fix the test

then before i open the pr, i git rebase -i main and rewrite it into the story i wish i'd told the first time:

add scheduler interface
wire scheduler into queue
cover scheduler edge cases with tests

what changed

i started planning prs backwards. before writing any code i'd jot down the 3-5 commits i wished existed at the end. then i'd just make the mess that gets there.

your git log is the spec you wish you'd written first.

this is also the cure for the "wait what did i actually change" feeling. you cannot review your own pr clearly if it's 47 unrelated commits.
